# 출시 전 체크리스트

작성: 2026-08-16 · 대상: 쌤플래너 학생 앱(Expo) · 과외쌤 웹(Next.js) · Supabase

여기저기 흩어져 있던 출시 블로커를 한곳에 모았다. `STOP-NEEDS-HUMAN.md`(2026-06-24) 는
자율 빌드 시점의 STOP 지점 목록이고, 이 문서는 **실제 출시를 막는 것**만 담는다.
겹치는 항목은 여기가 최신이다.

각 항목의 표기:
- **누가** — 🧑 사람만 가능(대시보드·계약·심사·키 발급) / 💻 코드로 가능 / 🧑💻 둘 다 필요
- **안 하면** — 실제로 벌어지는 일. "권장" 이 아니라 결과를 적는다.

---

## A. 지금 당장 사고가 나는 것 (출시 차단)

### A1. `mailer_autoconfirm = true` 해제 🧑
**무엇** 2026-06-24 테스트 편의로 켜 둔 설정. 링크된 Supabase 프로젝트에서 꺼야 한다.
Supabase → Authentication → Sign In / Providers → Email → "Confirm email" 켜기.
또는 `PATCH /v1/projects/{ref}/config/auth` 로 `{"mailer_autoconfirm": false}`.

**안 하면** 아무 이메일 주소로나 계정이 만들어진다(존재하지 않는 주소, 남의 주소 포함).
스팸 가입으로 무료 한도가 소진되고, 남의 이메일로 가입한 계정은 회수 수단이 없다.

**확인** 가입 후 인증 메일을 받기 전까지 로그인이 안 되면 성공.

### A2. CORS 허용 출처에 운영 도메인 등록 🧑
**무엇** Edge Function 이 `BROWSER_ALLOWED_ORIGINS` 환경변수로 출처를 제한한다
(`supabase/functions/_shared/`). 현재 localhost 만 들어 있다.
운영 도메인(과외쌤 웹, 학생 웹 빌드)을 콤마로 넣어야 한다.

**안 하면** **실사용자가 회원 탈퇴를 못 한다.** 탈퇴는 `account-delete` Edge Function 을
브라우저에서 호출하는데 CORS 에서 막힌다. 앱스토어 심사 리젝 사유이자 법적 요구사항 위반이다.
AI 검사 호출도 같은 경로로 막힌다.

**확인** 운영 도메인에서 탈퇴 화면을 열어 실제로 탈퇴가 되는지.

### A3. 약관·개인정보처리방침 본문 🧑💻
**무엇** 지금은 학생 앱 온보딩에 **동의 토글만** 있고 볼 수 있는 본문이 없다
(`apps/student/src/m1Screens.tsx` 약관 단계). 정식 문서를 만들고 화면에서 열 수 있게 연결해야 한다.
문서에는 최소한 수집 항목(이메일·이름·생년월일·학년·숙제 사진·공부 기록), 보관 기간,
제3자 제공(Anthropic 등 AI 처리), 파기 절차가 들어가야 한다.

- 🧑 문서 작성·법률 검토 · 호스팅 URL 확보
- 💻 화면에서 링크 연결

**안 하면** 내용 없는 동의는 동의가 아니다. 앱스토어·구글플레이 모두 심사에서 개인정보처리방침
URL 을 필수로 요구한다 — 없으면 제출 자체가 안 된다.

### A4. 과외쌤 웹 가입에 약관 동의가 아예 없다 💻
**무엇** 학생 앱에는 동의 단계가 있는데 과외쌤 웹 가입(`TeacherSignupContent`, `m1.tsx`)에는
동의 절차가 하나도 없다. 이메일·비밀번호만 받고 계정이 생긴다.

**안 하면** 과외쌤은 동의 없이 가입된 사용자가 된다. 과외쌤은 **학생의 개인정보를 다루는 쪽**이라
오히려 더 명확한 동의가 필요하다.

### A5. Supabase Free → Pro 🧑
**무엇** 유료 플랜으로 올린다.

**안 하면** Free 프로젝트는 일정 기간 미사용 시 **자동 정지**된다. 정지되면 앱 전체가 죽는다.
백업·로그 보관 기간도 Free 에서는 짧아 사고 시 복구가 안 된다.

## B. 돈·데이터가 걸린 것 (출시 차단)

### B1. 결제 실연동 🧑💻
**무엇** `billing-stripe` · `iap-webhook` Edge Function 이 **501 스텁**이다. 개발 중에는
`mock_set_teacher_subscription` / `mock_set_student_subscription` RPC 가 웹훅을 대신한다.

- 🧑 Stripe 계정·키 발급, RevenueCat/IAP 설정, 앱스토어 유료 계약 체결
- 💻 서명 검증·상태 전이 구현, mock RPC 를 프로덕션에서 차단

**안 하면** 결제가 되지 않거나, 더 나쁘게는 **mock RPC 가 살아 있어 결제 없이 구독 상태를
켤 수 있다.** 출시 전 mock RPC 권한 차단 여부를 반드시 확인할 것.

### B2. AI 키와 모델 확정 🧑💻
**무엇** `AI_CHECK_RESULTS_ENABLED = false` 로 판정 노출이 꺼져 있다(정확도 문제로 2026-08-07 중단).
모델(Haiku 4분할 vs Gemini 무분할)도 확정 전이다.

**안 하면** AI 검사가 제품의 핵심 판매 포인트인데 꺼진 채로 나간다. 프리미엄 가치가 없다.
켜기 전에 판정 정확도 재측정 결과가 있어야 한다(`docs/PROJECT-GUIDE.md` §3-2).

**연결** 한도(월 40회·100장)는 **Haiku 4분할 기준**으로 잡혀 있다
(`supabase/migrations/20260816000000_ai_check_limits_repricing.sql`).
Gemini 로 확정되면 한도를 되돌릴 수 있다 — 그 계산도 같은 파일에 있다.

### B3. 숙제 사진 180일 보관 정리를 실행하는 것이 없다 💻
**무엇** `homework_photos_expired_paths()` 는 "지울 대상 목록"만 돌려준다. **실제로 호출하는
스케줄러가 없다.** Storage 파일 삭제는 Storage API 가 필요해 Postgres 안에서 못 한다.

**안 하면** 개인정보처리방침에 "180일 보관" 이라고 써 놓고 실제로는 영구 보관하게 된다.
사진이 계속 쌓여 Storage 비용도 무한히 는다.

### B4. 탈퇴 시 Storage 정리 대기열에 처리기가 없다 💻
**무엇** 프로필 삭제 트리거가 `storage_purge_queue` 에 행을 넣고, `account-delete` Edge Function 이
그걸 처리한다. 그런데 그 함수를 **거치지 않고** `delete_my_account()` RPC 만 직접 부르면
대기열에 pending 이 남고 아무도 처리하지 않는다.

**안 하면** 탈퇴한 사용자의 숙제 사진이 Storage 에 그대로 남는다. "탈퇴하면 지웁니다" 가 거짓이 된다.

**함께** B3 와 같은 수단이 필요하다 — 주기적으로 도는 정리 작업 하나로 둘 다 처리하는 게 맞다.

### B5. 테스트 계정·데이터 정리 🧑💻
**무엇** 현재 원격 DB 에 검증용 계정이 남아 있다(2026-06 · 2026-08-04 생성분 12개).
`autoconfirm-check-*@example.com` 처럼 프로필 없는 auth 유저도 있을 수 있다.

**안 하면** 운영 데이터에 테스트 계정이 섞인다. 지표가 오염되고, 테스트 계정 비밀번호는
대개 공유돼 있어 보안 구멍이 된다.

## C. 스토어 제출에 필요한 것

### C1. 앱 식별자·아이콘·스플래시가 없다 🧑💻
**무엇** `apps/student/app.json` 에 `ios.bundleIdentifier` 와 `android.package` 가 **없다**.
아이콘·스플래시 자산도 없고 `eas.json` 도 없다. 버전은 `0.1.0` 그대로다.

**안 하면** 빌드 자체가 안 된다. 스토어 제출 이전 단계에서 막힌다.

### C2. 개인정보 라벨 · 카메라 권한 설명 🧑
**무엇** 앱스토어 개인정보 라벨(수집 항목 신고)과 데이터 안전 섹션(Play)을 채워야 한다.
카메라 권한 문구는 이미 있다("집중 모드에서 기기 안에서만 확인") — 실제 동작과 일치하므로 그대로 쓰면 된다.

**안 하면** 심사 리젝. 실제 수집과 라벨이 다르면 사후 제재 대상이다.

### C3. 회원 탈퇴 도달 경로 ✅ (완료)
학생 앱 설정 → 탈퇴 경로는 연결됨. **단 A2(CORS)가 안 되면 눌러도 실패한다** — 함께 확인할 것.

## D. 있으면 사고를 줄이는 것 (차단은 아님)

### D1. 푸시 알림 💻
**무엇** 앱 내 알림(`notifications` 테이블 + 트리거)은 동작한다. **앱 밖 푸시는 없다.**
`push_tokens` 테이블은 있으나 아무도 쓰지 않는다.

**안 하면** 숙제가 나가도 학생이 앱을 열기 전까지 모른다. 리텐션에 직접 영향은 있지만
기능 자체는 성립한다.

### D2. 에러 모니터링이 없다 💻
**무엇** Sentry 등 에러 수집이 한 곳도 없다.

**안 하면** 사용자가 겪는 오류를 알 방법이 없다. 문의가 와야 비로소 안다.

### D3. 이메일 발신 도메인 🧑
**무엇** 인증·재설정 메일이 Supabase 기본 메일러로 나간다. 발신 한도가 낮고 도메인이 우리 것이 아니다.
커스텀 SMTP 설정 권장.

**안 하면** 가입이 몰리면 인증 메일이 안 나간다. 스팸함으로 갈 확률도 높다.

### D4. 강제 업데이트 값 관리 🧑
**무엇** `app_config.min_supported_build` 가 기본값 1 이다. 스토어 빌드 번호 체계를 정하고
값을 맞춰야 의미가 생긴다.

**안 하면** 치명적 버그가 나가도 구버전 사용을 막을 수 없다.

### D5. E2E 실행 🧑💻
**무엇** Playwright(teacher) / Maestro(student) 스캐폴딩만 있고 실행 이력이 없다.

**안 하면** 회귀를 사람이 손으로 잡아야 한다.

## 실행 순서 제안

1. **A2 → A1 → A5** — 인프라·설정. 코드 변경이 없고 즉시 효과가 있다.
2. **A3 → A4 → C1 → C2** — 스토어 제출 준비. A3 문서가 C2 라벨의 입력이므로 순서가 있다.
3. **B3 + B4** — 정리 작업 하나로 묶어서 구현.
4. **B1 → B2** — 결제와 AI. 둘 다 사람의 계약·판단이 선행한다.
5. **B5** — 출시 직전에 한 번 더. 그 사이 검증하며 또 쌓인다.

## 이 문서를 갱신하는 규칙

항목을 끝내면 지우지 말고 ✅ 로 바꾸고 언제·누가 했는지 한 줄 남긴다 —
"이거 했었나?" 를 다시 조사하는 비용이 더 크다.
