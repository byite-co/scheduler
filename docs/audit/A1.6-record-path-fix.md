## 1. 수정 전후

### 1-1. enum 캐스팅 (작업 1)

**before** — `20260807030000_homework_check_observation.sql:87`
```sql
set status = case when p_discard_reason is null then 'completed' else 'failed' end,
```
CASE 의 두 분기가 모두 무형(unknown) 리터럴이라 결과 타입이 **text** 로 확정된다.
Postgres 는 `text → enum` 을 암시적으로 캐스팅하지 않으므로 대입에서 죽는다.

실측 근거:
```
select pg_typeof(case when true then 'completed' else 'failed' end);            → text
select pg_typeof(case when true then 'completed'::check_attempt_status
                       else 'failed'::check_attempt_status end);                → check_attempt_status
```

단일 리터럴 대입(`set status = 'completed'`)은 unknown 이 대상 타입으로 해석돼 잘 된다 —
그래서 같은 파일의 다른 UPDATE 는 멀쩡하고 이 한 줄만 깨졌다.

**after** — 분기마다 명시 캐스팅. 한쪽만 캐스팅해도 CASE 전체가 그 타입으로 해석되지만
**둘 다** 적었다. 나중에 분기를 추가하는 사람이 캐스팅 없는 리터럴을 넣어 같은 사고를
반복하지 않게 하려는 것이다.
```sql
set status = case
               when p_discard_reason is null then 'completed'::check_attempt_status
               else 'failed'::check_attempt_status
             end,
```

`error_code` 쪽 CASE 는 대상이 **text 컬럼**이라 문제가 없다 — 그대로 뒀다.

### 1-2. 폐기 기록을 막던 제약 (작업 중 발견)

캐스팅을 고치고 **실행 테스트를 돌리자** 성공 경로는 통과했는데 폐기 경로가 죽었다:
```
new row for relation "homework_check_attempts" violates check constraint "attempts_completed_has_result"
```

같은 마이그레이션(20260807030000) 안에서 함수와 제약이 서로를 부정하고 있었다.

| | 내용 |
|---|---|
| 함수 | 폐기 시 `status='failed'` 로 두고 `raw_ai_observation` 은 **그대로 저장**. 주석에도 "폐기한 원본도 남긴다 — 무엇이 왜 폐기됐는지 못 보면 프롬프트를 고칠 근거가 없다" |
| 제약 | `(status = 'completed') = (verdict is not null or raw_ai_observation is not null)` — **양방향**이라 "결과가 있으면 반드시 completed" 까지 강제 |

→ `failed` + 관찰 있음 = `false = true` → 위반. **폐기 경로는 성공할 수 없었다.**

캐스팅 버그에 가려 여태 아무도 여기까지 도달하지 못했다.

**after** — 양방향 등식을 의도대로 **단방향 두 개**로 쪼갰다.
```sql
constraint attempts_completed_has_result
  check (status <> 'completed' or verdict is not null or raw_ai_observation is not null)
constraint attempts_verdict_requires_completed
  check (verdict is null or status = 'completed')
```
`raw_ai_observation` 은 `failed`(폐기)에도 있을 수 있다 — 그게 폐기 기록이다.
옛 이름 `attempts_verdict_only_when_completed` 는 20260807030000 이 이미 드롭했고
"없어야 한다"는 단정이 있으므로 재사용하지 않았다.

> **범위 판단**: 작업 1은 "캐스팅 수정"만 지시했다. 그런데 이걸 안 고치면 검증 실패한 AI 응답의
> 원본이 **하나도 남지 않는다** — 관찰 재설계의 목적 자체가 불가능한 상태로 남는다.
> 폐기 테스트를 빼서 초록을 만드는 것은 알려진 결함을 감추는 것이라, 고치고 여기 적는다.

### 1-3. 이중 방어 fail-open → fail-closed (작업 5)

**before** — `20260816020000`
```sql
if coalesce(auth.role(), 'service_role') <> 'service_role' then
```
role 을 못 읽으면 통과. "모르면 열린다"는 방향이다.

**after** — 클레임의 **존재 여부**로 갈라 API 경로에서는 언제나 닫는다.
```sql
jwt_claims text := nullif(current_setting('request.jwt.claims', true), '');
jwt_role   text := nullif(current_setting('request.jwt.claim.role', true), '');
...
if (jwt_claims is not null or jwt_role is not null)
   and coalesce(auth.role(), '') <> 'service_role' then
  raise exception 'service_role_required';
end if;
```

| 경로 | 클레임 | 결과 |
|---|---|---|
| anon 키 | 있음(role=anon) | 거부 |
| 사용자 토큰 | 있음(role=authenticated) | 거부 |
| 클레임은 있는데 role 을 못 읽음 | 있음 | **거부**(모르면 닫힌다) |
| service_role 키 | 있음(role=service_role) | 통과 |
| psql·Management API·마이그레이션 | 없음 | 통과 |

구형 GUC(`request.jwt.claim.role`)도 함께 본다 — 한쪽만 보면 클레임 형식이 바뀔 때 뚫린다.

## 3. 같은 클래스 버그 수색 결과 (작업 2)

레포 grep 만으로는 컬럼 타입을 모른다. 라이브 DB 의 **실제 enum 컬럼 목록**(22개)을 뽑아
모든 함수 본문의 `set <컬럼> = case …` 패턴과 대조했다.

| 위치 | 컬럼 타입 | 판정 |
|---|---|---|
| `record_homework_check_observation` — `status = case … 'completed'/'failed'` | `check_attempt_status` **(enum)** | 🔴 **버그 — 이번에 수정** |
| `complete_storage_purge` (`20260810000000:124`) — `status = case … 'done'/'failed'` | `storage_purge_queue.status` = **text** | ✅ 정상. 이 표는 enum 을 쓰지 않는다. 실제로도 계정 삭제 시 `status='done'` 으로 기록된 행을 확인했다 |
| `20260623000000_m3_timer_sessions.sql:22` — `timer_state = case … 'running'/'completed'` | enum 컬럼 목록에 없음(text) | ✅ 정상. 일회성 백필 DML |
| `complete_homework_check_attempt` (`:232`) — `confidence = case … null/greatest(...)` | numeric | ✅ 정상 |
| `apply_homework_ai_verdict` — `ai_confidence = case … null/greatest(...)` | numeric | ✅ 정상 |
| `record_homework_check_observation` — `error_code = case … null/'observation_discarded'` | text | ✅ 정상 |

**enum 컬럼에 무형 CASE 를 대입하는 곳은 레포 전체에서 한 곳뿐이었다.**
(`complete_storage_purge` 는 컬럼명이 같아 자동 스캔에 걸렸을 뿐, 타입이 text 라 무해하다.)

⚠️ 다만 **같은 함정이 다시 생길 여지**는 남아 있다. 단일 리터럴 대입은 잘 되므로
`set status = 'completed'` 를 보고 "리터럴이면 되는구나" 하고 CASE 를 쓰면 그대로 깨진다.
막는 방법은 문자열 규칙이 아니라 **실행 테스트**다 — 그래서 §2 를 추가했다.

## 4. 돈이 새는 순서 (작업 4 — 조회만, 구조 변경 없음)

### 4-1. 순서

`supabase/functions/ai-homework-check/index.ts` 기준:

```
247  start_homework_check_attempt        (attempt 생성 — 비용 0)
300  try {
303    downloadSnapshotImages            (사진 다운로드)
318    for (배치) callObservationBatch    ← 🔴 여기서 AI 비용 발생
329      totalCost += …                  (합산은 메모리에만)
361  } catch → failAttempt(code)         ← 비용 기록 없이 실패 마감
383  record_homework_check_observation   ← 비용을 DB 에 남기는 **유일한** 지점
397  if (writeError) → fail_homework_check_attempt("attempt_complete_failed")
```

### 4-2. 기록이 실패하면 비용은 유실된다

`fail_homework_check_attempt`(schema.sql:740) 가 쓰는 컬럼:
```sql
set status = 'failed', error_code = …, completed_at = now(), updated_at = now()
```
**`model`·`input_tokens`·`output_tokens`·`estimated_cost_usd_micros`·`latency_ms` 를 남기지 않는다.**

따라서:

| 실패 시점 | 비용 | 이력 |
|---|---|---|
| AI 호출 중 예외(`catch`) | **이미 나감**(부분 배치까지) | `failAttempt` — 비용 0으로 남음 |
| AI 성공 후 기록 실패(`writeError`) | **전액 나감** | `fail_homework_check_attempt` — 비용 0으로 남음 |

**2026-08-07 이후 벌어진 일이 정확히 두 번째 경우다.** AI 는 정상 호출돼 돈이 나갔고,
결과를 저장하려는 순간 캐스팅 오류로 실패해, 비용도 관찰 원본도 **아무것도 남지 않았다.**

### 4-3. 재시도가 AI 를 다시 호출하는가 — **한다**

- `start_homework_check_attempt` 는 `(requested_by, idempotency_key)` 유니크로 멱등이다.
  같은 키로 재전송하면 **기존 attempt 행을 돌려준다.**
- 그러나 Edge Function 은 그 뒤 코드를 그대로 이어가 **AI 를 다시 호출한다.**
  멱등 보호는 *attempt 행 생성*에만 걸려 있고 *AI 호출*에는 걸려 있지 않다.
  이미 마감된 attempt 였다면 기록 단계에서 `check_attempt_not_open` 이 나서 **비용만 나가고 또 버려진다.**
- 클라이언트 키는 `${submissionId}:${submissionKey}`(`m4Screens.tsx:184`). 사용자가 다시 제출하면
  새 submission → 새 키 → 새 attempt → **같은 사진에 대한 AI 재호출**(제출당 3회 한도 안에서).

즉 **이중 과금 경로가 실재한다.** 구조 변경은 지시대로 하지 않았다. 고치려면 재전송 시
"이미 완료된 attempt 면 AI 호출 전에 그 결과를 반환"하는 분기가 `start` 직후에 필요하다.

### 4-4. 8/7 이후 실패 기록 건수 — **집계 불가**

```sql
select count(*) total,
       count(*) filter (where status='failed') failed,
       count(*) filter (where status='failed' and created_at >= '2026-08-07') failed_since_0807,
       count(*) filter (where estimated_cost_usd_micros > 0) with_cost
from homework_check_attempts;
→ total 0 · failed 0 · failed_since_0807 0 · with_cost 0
```

표가 **비어 있다.** 8/7 이후의 스모크 테스트·검증 데이터는 이후 작업들의 테스트 정리 과정에서
계정과 함께 삭제됐다(`homework_check_attempts` 는 `submission_id`/`requested_by` 로 연쇄 삭제된다).
Supabase 로그로 역산하는 것도 보존 기간(Free 플랜 1일)을 넘겨 불가능하다.

**말할 수 있는 것은 이것뿐이다**: 8/7 이후 성공적으로 기록된 관찰은 **0건**이며
(함수가 항상 실패했으므로 논리적으로 확정), 그동안 나간 AI 비용의 총액은 **확인할 수 없다.**
실사용자가 0명이고(A1 §3-10) 호출은 개발 중 스모크 테스트뿐이었으므로 금액 자체는 작을 것이다.
