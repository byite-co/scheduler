## 1. 클래스의 정체 — 왜 조용히 통과하나

세 가지가 겹쳐야 사고가 된다.

1. **`indexOf` 가 -1 을 돌려준다** (앵커 오타·이름 변경·줄바꿈 불일치).
2. **`slice(start, -1)` 은 오류가 아니다.** "끝에서 한 글자 뺀 문자열" 이다 →
   창이 **파일 거의 전체**로 벌어진다.
3. 그 창에 대고 `toContain(...)` 을 하면 **무엇을 단정하든 통과**한다.

실측 대조(같은 상황에서 앵커만 깨뜨림):

```
예전: slice(start, -1) → 창 97자 → toContain("accept_connection_request") → 통과 (거짓 초록)
지금: '끝 앵커 없음: ANCHOR_GONE' 던짐                                   → 거짓 초록 불가
```

반대 방향도 있다. 끝 앵커를 **파일 처음부터** 찾으면 시작보다 앞선 등장에 걸려
`end < start` → slice 가 **빈 문자열** → 이번엔 무엇을 단정하든 **실패**한다.
PR #55 의 CI 실패가 정확히 이 모양이었다(로컬 CRLF 에서는 -1 → 거짓 초록,
CI LF 에서는 앵커가 매칭되며 앞선 등장에 걸려 빈 문자열 → 실패).

## 2. 전수 조사 결과 (14건)

`packages/shared/src/*.test.ts` **39개 파일**을 기계적으로 훑어
`slice(x.indexOf(A), x.indexOf(B))` 패턴을 추출한 뒤, 각 패턴을 **실제 소스에 적용해**
CRLF·LF 양쪽에서 창이 어떻게 되는지 계산했다.

| 파일 | 건수 | 끝 앵커에 `\n` | CRLF 결과 | LF 결과 |
|---|---|---|---|---|
| `m1.accept.test.ts` | 6 | 없음 | 전부 정상 | 전부 정상 |
| `m1.immutableColumns.test.ts` | 5 | 없음 | 전부 정상(1건은 `+700` 고정창) | 동일 |
| `m1.schema.test.ts` | 2 | 없음 | 정상 | 정상 |
| `m7.schema.test.ts` | 1 | 없음 | 정상 | 정상 |
| `r3.schema.test.ts` | (3) | **2건 있었음** | **거짓 초록** | **빈 문자열 → 실패** |

**결론: 활성 거짓 초록은 `r3.schema.test.ts` 뿐이었다.** 나머지 14건은 앵커에 `\n` 이 없고
끝 앵커의 첫 등장이 이미 시작 이후라서, 지금은 CRLF·LF 에서 **같은 창**을 만든다.

그러나 14건 전부 **잠재**다 — 앵커 문자열 하나만 바뀌면(리팩터링·문구 수정) 즉시 1번 항목의
거짓 초록으로 떨어진다. A1~A5.1 의 보안 단정이 다수 여기 걸려 있어(`guard_*` 트리거,
컬럼 권한 허용목록, `fees_teacher_rw` 정책, `storage_purge_queue` 스키마) 그대로 두지 않았다.

## 4. 조치 — `못 찾으면 던진다`

`packages/shared/src/testSource.ts`:

| 함수 | 역할 | 실패 시 |
|---|---|---|
| `readSource(url)` | 읽을 때 CRLF→LF 정규화 | — |
| `sliceBetween(src, A, B)` | `A` 이후에서만 `B` 를 찾아 창을 만든다 | **던진다** (어느 앵커인지 지목) |
| `sliceFrom(src, A, len)` | 끝 앵커가 마땅치 않은 고정 창 | 시작 앵커 없으면 **던진다** |
| `codeOnly(src)` | 줄 주석(`//`, `--`) 제거 | — (주석 산문 오탐 방지) |

교체: `m1.accept` 6건 / `m1.immutableColumns` 5건(1건은 `+700` → `sliceFrom`) /
`m1.schema` 2건 / `m7.schema` 1건. 네 파일의 소스 읽기도 `readSource` 로 바꿨다.

**창의 내용은 이전과 동일하다** — 14건 전부 "끝 앵커의 첫 등장이 이미 시작 이후" 임을
사전에 계산해 확인했으므로, `fromIndex` 를 줘도 같은 위치를 찾는다.
바뀐 것은 **못 찾았을 때의 거동**뿐이다.

## 5. `.gitattributes` — 커밋 두 개로 분리

### (a) 규칙 추가 — `4f58deb`

```
* text=auto eol=lf
*.png binary   (+ jpg/jpeg/gif/webp/ico/pdf/woff/woff2/ttf/otf/mp4/zip)
```

⚠️ **바이너리를 명시한 이유**: UI 카탈로그 PNG **187장**이 추적되고 있다.
`text=auto` 의 자동 판별에만 맡기면 변환 사고 시 파일이 깨진다. 명시로 위험을 제거했다.
재정규화에서 PNG 는 **0건** 포함됐음을 확인했다.

### (b) 재정규화 — `4afd96a`

**`git add --renormalize .` 는 아무것도 스테이징하지 않았다.** 저장소 텍스트 파일이 이미
전부 LF 였기 때문이다. 확인 방법: 추적 중인 텍스트 확장자 전부의 blob 에서 CR 바이트를 셌고,
**단 하나** `apps/teacher/src/app/m6.tsx` 만 CR 을 갖고 있었다.

바이트 단위로 본 실제 상태 — **CRLF 276쌍 + 단독 CR 1개**(혼합):

```
byte 2038 (57번째 줄 근처):
  const billing = getTeacherBillingState(status);\r\r\n
```

줄 끝에 CR 이 하나 더 붙은 흔적이다. 문자열 리터럴 내부가 아니라 후행 공백이라 JS 의미에는
영향이 없다. 예전 세션에서 `\r?\n` 정규식으로 편집할 때 남은 잔재로 보인다(A4 에서 같은
함정을 한 번 기록했다). 이 단독 CR 때문에 git 이 자동 정규화를 하지 않은 것으로 보인다.

그래서 이 파일만 명시적으로 LF 로 바꿨다(CR 277개 제거, 11976 → 11699 바이트).

**내용 변경 0 확인**: `git diff --ignore-all-space` 결과가 **비어 있다**.
diff 규모 `276 insertions / 276 deletions` 은 전부 줄바꿈이다.
이 파일은 `m6.schema.test.ts` 가 문자열로 단정하는 대상이라, 혼합 줄바꿈을 남겨 두면
이번에 막은 거짓 초록 클래스의 씨앗이 된다.

### 효과 — 개발자 설정과 무관해졌다

`.gitattributes` 적용 후, **로컬 `core.autocrlf` 오버라이드를 제거하고** 재체크아웃했다.
Git for Windows 의 system `core.autocrlf=true` 가 살아 있는데도 워킹트리는 **LF** 다:

```
m5.tsx CR: 0 · m6.tsx CR: 0 · m1.accept.test.ts CR: 0
```

즉 `eol=lf` 가 system 설정을 덮어쓴다 → 이제 **모든 개발자가 같은 줄바꿈**을 받는다.
이번 사고의 토양이 제거됐다.

그 상황에서도 단정이 흔들리지 않아야 한다 — `readSource` 가 그것을 보장한다.
