## 1. 작업 1 — 재부여 실측

A2 에서 `drop`+`create` 한 것과 `create or replace` 한 것을 전부 확인했다.
`fail_homework_check_attempt` 는 default 인자를 붙이며 시그니처가 바뀌어 **drop 후 재생성**했으므로,
권한이 제대로 다시 붙었는지가 실제 위험이었다.

### 롤별 EXECUTE 목록 (라이브 실측)

```sql
select p.proname, p.prosecdef as definer,
       (select string_agg(distinct rp.grantee, '+' order by rp.grantee)
          from information_schema.routine_privileges rp
         where rp.specific_name = p.proname||'_'||p.oid) as grantees,
       position('service_role_required' in pg_get_functiondef(p.oid)) > 0 as has_inner_guard
from pg_proc p join pg_namespace n on n.oid=p.pronamespace and n.nspname='public'
where p.proname in (...);
```

| 함수 | definer | 내부 이중 방어 | grantees |
|---|---|---|---|
| `fail_homework_check_attempt` (drop+create) | ✅ | ❌ | postgres + service_role |
| `claim_homework_check_attempt` (신규) | ✅ | ❌ | postgres + service_role |
| `record_homework_check_observation` | ✅ | ❌ | postgres + service_role |
| `apply_homework_ai_verdict` | ✅ | **✅** | postgres + service_role |
| `start_homework_check_attempt` | ✅ | ❌ | postgres + service_role |
| `complete_homework_check_attempt` | ✅ | ❌ | postgres + service_role |

**anon·authenticated 에 열린 것은 없다.** 회수할 것이 없어 추가 회수는 하지 않았다.

내부 이중 방어(`service_role_required`)는 `apply_homework_ai_verdict` 에만 있다.
그 함수만 A1.5 에서 **anon EXECUTE 가 실제로 열려 있던 전례**가 있어 이중 방어를 넣었고,
나머지 5개는 처음부터 service_role 전용으로 만들어져 그런 전례가 없다.
지금 추가하지 않은 이유: 6개 모두에 같은 가드를 붙이면 **파이프라인 RPC 가 Management API·psql
경로에서도 동작해야 하는데**(운영 점검·데이터 보정) 가드가 그 판단을 각 함수에 흩뿌린다.
권한 회수가 1차 방어선이고 실측으로 닫혀 있음을 확인했으므로 현 상태를 유지한다.
⚠️ 다만 이 함수들 중 하나라도 나중에 grant 가 되돌려지면 즉시 뚫린다 — 아래 음성 테스트가 그 감시다.

## 2. 작업 2 — claim 만료·재획득

### 문제

A2 의 claim 은 `ai_started_at is null` 일 때만 성공했다. 권리를 가져간 요청이 크래시하면
(Edge Function 타임아웃·프로세스 종료·네트워크 단절) 그 행은
`status='processing'` + `ai_started_at` 채워진 상태로 **영구히** 남는다. 그러면

- 같은 키 재시도 → claim 실패 → 409 `check_already_in_progress`
- 다른 키 재시도 → 부분 유니크 인덱스(`one_active_idx`)가 막아 `check_already_in_progress`

즉 **그 제출은 다시는 검사할 수 없다.** 아무도 돌고 있지 않은데 영원히 "진행 중"이다.

### 해결 — 소유가 아니라 리스(lease)

```sql
where id = p_attempt_id
  and status in ('queued', 'processing')
  and (
    ai_started_at is null
    or ai_started_at < now() - make_interval(mins => ai_check_claim_lease_minutes())
  );
```

`ai_check_claim_lease_minutes()` = **10**.

**임계를 10분으로 잡은 근거**
- 정상 실행: 사진 최대 9장 = 배치 3회, 배치당 수~수십초 → 최악 1~2분.
- Supabase Edge Function 의 벽시계 상한이 그보다 짧다 — 살아 있는 실행은 10분을 넘길 수 없다.
  10분이 지났다면 그 실행은 확실히 죽었다.
- 너무 짧으면(1분) 느린 실행이 아직 도는 중에 두 번째 요청이 탈환해 **AI 를 두 번 부른다** —
  막으려던 것을 스스로 다시 여는 셈이다.
- 너무 길면(1시간) 학생이 그동안 재시도를 못 한다.

**탈환은 리스만 갱신한다.** `ai_started_at`·`updated_at` 외에는 손대지 않는다 —
죽은 실행도 AI 를 이미 불렀을 수 있고 그 토큰·비용은 실제로 나간 돈이다.

## 4. ⚠️ 남는 한계 — 탈환 후 record 가 이전 비용을 덮는다

시나리오 F 의 최종 비용은 **500**(2회차 값)이었다. 1회차 1234 는 사라졌다.

- **claim 은 비용을 보존한다** (C 에서 1234 확인). 지시된 요구는 충족한다.
- 그런데 그 뒤 `record_homework_check_observation` 이 `coalesce(p_cost, 기존값)` 으로
  갱신하므로, 2회차가 값을 넘기면 **1회차 비용이 대체된다.**

이걸 더하기로 바꾸면 같은 실행의 재시도에서 이중 계상이 된다 — `coalesce` 는 "null 로 덮지
말라"는 뜻이지 "누적하라"는 뜻이 아니다. **한 행에 한 번의 비용만 담는 현재 구조에서는
재획득된 실행의 1회차 비용을 정확히 누적할 수 없다.**

정확한 누적이 필요하면 attempt 당 다건을 담는 **별도 비용 원장**이 필요하다(구조 변경, 범위 밖).
실무 영향: 재획득은 크래시라는 예외 상황에서만 일어나고, 금액은 1회분(수십 원)이다.
파일럿 비용 집계에서 **과소 계상될 수 있다**는 점을 알고 보면 된다.
