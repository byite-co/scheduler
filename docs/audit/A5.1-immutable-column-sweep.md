### 재발 방지 — 적용 워크플로

원인은 단순하다. **Management API 의 `POST /v1/projects/{ref}/database/query` 로 SQL 을 실행하면
`supabase_migrations.schema_migrations` 에 아무것도 남지 않는다.** CLI 의 `db push` 만 이력을
기록한다. 이 세션들은 CLI 로그인이 TTY 를 요구해 API 경로를 써 왔고, 그래서 14개가 새 나갔다.

**표준은 `pnpm sb db push` 다.** 가드(`scripts/supabase-guard.mjs`)가 대상 ref 를 검사하고,
CLI 가 적용과 이력 기록을 원자적으로 함께 한다. 마이그레이션을 적용하는 정상 경로는 이것 하나여야 한다.
API 경로는 **조회 전용**으로 쓴다 — `storage.objects`·`auth.users`·`pg_policy` 처럼 PostgREST 로
못 보는 것을 읽을 때, 그리고 RLS 재현 실험에.
TTY 문제 등으로 부득이 API 로 적용해야 한다면 **같은 호출 안에서 이력 행까지 넣는다**
(A5.1 에서 그렇게 했다: 마이그레이션 실행 → 곧바로 `insert into schema_migrations`).
적용과 이력 기록이 분리되는 순간 다시 어긋난다. 어느 쪽을 택했든 마무리는
`pnpm sb db push --dry-run` 으로 `Remote database is up to date.` 를 눈으로 확인하는 것이다.

## 2. 이 클래스가 무엇인가

A5 에서 `connections.student_id` 로 처음 나온 결함의 일반형:

> **UPDATE 정책이 소유자만 확인하고, 그 행에 불변이어야 할 다른 컬럼이 있으면 소유자가 그 컬럼을 자유롭게 바꿀 수 있다.**
> `with check` 는 UPDATE **후** 행만 보고 `OLD` 를 참조할 수 없으므로 "이 컬럼은 안 바뀌었다" 를
> 정책으로 표현할 방법이 없다.

전수 조사 중에 **판정 기준**이 하나 정리됐다:

| 소유 판정 방식 | 결과 | 예 |
|---|---|---|
| 소유 컬럼이 `with check` 에 **직접** 나온다 | **안전** — 사후 이미지가 검사돼 바꿀 수 없다 | `study_sessions.student_id` → 42501 |
| 소유는 다른 컬럼/서브쿼리로 판정하고, **권한을 가진 다른 컬럼**이 있다 | **뚫림** | `connections`(teacher_id 검사 / student_id 자유) · `profiles`(id 검사 / role 자유) |
| 소유 판정에 **연결 요건**이 함께 있다 | **안전** — 귀속을 바꾸려면 그 학생과 연결이 있어야 한다 | `lessons` · `exam_records` → 42501 |

도구 선택도 여기서 갈린다:

- 클라이언트가 그 컬럼을 **아예 안 쓴다** → **컬럼 권한** 회수 (권한 층이 RLS 보다 먼저, 우회 표현식 없음)
- 클라이언트가 **같은 값으로 매번 실어 보낸다**(upsert) → **트리거**. 컬럼 권한은 값이 같아도 막으므로 화면이 깨진다
- 문제가 **INSERT 에도 있다** → **정책**. 컬럼 권한은 INSERT 를 막지 못한다

## 3. 전수 스캔 결과

UPDATE 를 허용하는 정책 **20개 / 17개 표**를 전부 조사했다(`polcmd in ('w','*')`).

> ⚠️ **판정 방법을 한 번 고쳐 잡았다.** 1차 측정에서 "오류가 안 났다 = 뚫림" 으로 셌는데,
> **정책에 걸려 0행이 매칭된 UPDATE 도 오류를 내지 않는다.** `학생이 자기 연결 status 변경` 이
> 그 함정에 걸려 "통과" 로 나왔다(실제로는 영향 0행). 2차부터 **영향 행 수와 조회값**으로 판정했다.
> 아래 표는 전부 2차 기준이다.

### 3-1. 뚫려 있었고 고친 것

| # | 표 · 컬럼 | 실행 주체 | 실측 (수정 전) | 실측 (수정 후) | 도구 |
|---|---|---|---|---|---|
| 1 | `profiles.role` | 학생 | **role=teacher 로 승격됨** (영향 1행, 조회값 `teacher`) | `P0001 role_is_not_self_assignable` | 트리거 |
| 2 | `todos` DELETE | 학생 | **잠긴 선생님 숙제가 지워짐** (남은 행 0건) | `P0001 students_cannot_delete_teacher_todos` | 트리거 |
| 3 | `reports.share_token` `share_expires_at` | 교사 | **`ATTACKER` 로 덮어써짐** | `42501` | 컬럼 권한 |
| 4 | `reports.student_id` | 교사 | **미연결 학생으로 갈아 끼워짐** | `42501` | 컬럼 권한 |
| 5 | `invite_codes.used_by` | 교사 | **임의 학생으로 채워짐** | `42501` | 컬럼 권한 |
| 6 | `lesson_fees.student_id` + INSERT | 교사 | **미연결 학생으로 변경 + 미연결 학생에게 999,999원 청구 생성** | 둘 다 `42501` | 정책(연결 요건) |
| 7 | `connections` INSERT | 학생 | **초대 코드 없이 임의 교사에게 pending 생성** (`invite_code=null`) | `42501` | 정책 삭제 + 권한 회수 |

**왜 심각한가 — 3·4·7 만 부연한다.**

- **3+4 를 합치면** 동의하지 않은 학생 이름의 리포트를 공개할 수 있다. `share_token` 은
  **로그인 없이 열리는 학부모 리포트의 유일한 자격증명**이다. 추측 가능한 값으로 바꿀 수 있고,
  `student_id` 를 미연결 학생으로 바꿀 수 있었다(정책의 `with check` 가
  `teacher_id = auth.uid() OR <active 연결>` 이라 **첫 가지만으로 통과**한다).
  토큰은 원래 `create_report_share`(security definer)만 만든다 — 직접 컬럼 쓰기는 그 생성기를 지나쳤다.
- **7 은 A5 의 시도 제한을 지나가는 두 번째 입구였다.** A5 는 `request_connection_by_invite` 를
  유일한 입구로 가정하고 그 안에 10분 10회를 넣었는데, 표에 직접 INSERT 하는 길에는
  코드 검증도, 시도 기록도, `disclosure_settings` 생성도 없었다.
  실제 악용 난이도는 "교사 UUID 를 알아야 한다" 로 제한된다(profiles RLS 가 연결된 교사만 읽게 하므로
  사실상 추측 불가). 즉 **당장 뚫리는 구멍보다는, 방어를 한쪽 입구에만 걸어 둔 구조 문제**다.

| 질문 | 답 | 근거 |

| 학생이 `status` 를 임의 전이할 수 있나? | **아니다** | 영향 **0행**. 학생용 UPDATE 정책이 애초에 없다 |
| 학생이 스스로 `active` 를 만들 수 있나? | **아니다** | `42501` |
| 학생이 초대 절차 없이 연결을 만들 수 있었나? | **그렇다 → 막았다** | `conn_student_insert_pending` 이 `teacher_id` 를 안 보고 초대 코드도 요구하지 않았다(§3-1 #7) |

즉 **UPDATE 쪽은 이미 대칭이 맞아 있었고**(A5 의 조치가 양쪽에 걸렸다), 비대칭은 **INSERT 쪽**에 있었다.
교사에게는 연결을 만드는 권한이 없는데 학생에게는 있었고, 그 권한에 초대 코드 요건이 없었다.

## 8. 확인 불가 / 남긴 항목

| 항목 | 상태 |
|---|---|
| 만14세 연령·보호자 동의 검증 | 학생이 `birth_date`·`guardian_consented_at` 를 자기 신고한다. 권한 문제가 아니라 검증 부재이고, 검증 수단(본인인증 등)은 별개 결정이다 |
| `push_tokens` 토큰 값 검증 | 푸시 미구현 상태에서 형식 검증을 넣으면 근거 없는 제약이 된다. 푸시 구현 시점의 항목으로 남긴다 |
| `study_sessions` 자기 신고 값 | 타이머 값을 서버가 독립 검증할 수단이 없다. 리포트가 이 값을 쓴다는 사실을 한계로 기록한다 |
| sweep 의 20행 예산 | A5 에서 기록한 한계가 이번에도 재현됐다 — 전체 테스트 스위트 뒤 소진에 **3회** 호출이 필요했다(30행) |
| 화면 실제 렌더 확인 | `apps/` 를 바꾸지 않았다. 정상 흐름이 깨지지 않는지는 실계정 실행 테스트 쌍(§5 의 2·4·6·7·10·12·14·15)으로 확인했다 |
| `reports.status`/`sent_at` 임의 지정 | 교사 소유 데이터로 판단해 허용 목록에 남겼다. 발송 이력의 정본은 `report_deliveries` 다 |
